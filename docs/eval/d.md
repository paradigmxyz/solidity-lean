# Lane D: Std.Do / vcgen with externally supplied invariants

Lead's own lane. Files: `Verify/Eval/D/{Bridge,Source,Loop,Robust,SpacerInv}.lean`,
`Verify/Eval/D/Scale/*.lean` (generated by `scripts/eval/gen_d_scale.py` from lane A's fixtures),
`scripts/eval/gen_spacer_inv.sh`. Every number below is one run on the hosted Hand (5 vCPU,
14 GB, `LEAN_NUM_THREADS=1`), toolchain v4.35.0, through `scripts/eval/check.sh`; `#timed` is
one declaration's elaboration including its kernel check, kernel is `#kernel_recheck` (the
kernel alone, re-adding the saved term), DAG is distinct subterms after `ShareCommon` (aux
declarations listed separately), tree is capped at 10,000,000. Peak RSS is per file and is
dominated by the imports (2.5 to 2.6 GB for every file here unless noted).

## What exists in 4.35 (and what changed from 4.34.1)

* Two WP frameworks. `Std.Do` (PostShape-based; `mvcgen`) is unchanged from 4.34.1 except
  that `mvcgen` is now `deprecated_syntax` ("use vcgen instead", since 2026-08-21). `Std.WP`
  (19 files, 4,775 lines) and `Lean/Elab/Tactic/VCGen` (the SymM-based `vcgen` driver,
  15 files, 3,394 lines) are new in 4.35.0 and gated by `experimental.vcgen` (a warning per call
  otherwise). `Lean/Meta/Sym` changed additively (LetToHave, LiftLet, normNumLit; internal edits
  to Pattern, Canon, Simp/Theorems, EvalGround). API risk: high for `vcgen`/`Std.WP` (new and
  experimental), moderate for `Sym.Apply`/`Grind.Goal` (present in 4.34.1, additive changes),
  deprecation for `mvcgen`.
* No instance was added: `SolM = StateT Storage (Except Revert)` already has
  `Std.WP.WP`/`WPMonad` (assertions `Storage → Prop`, exception postcondition
  `Revert → Prop`) and `Std.Do.WP` (shape `.arg Storage (.except Revert .pure)`).

## The bridge (no new trusted model)

`loom_wp_eq_stdWP : wp x post herr s = Std.WP.wp x (fun a s' => post a herr s') herr s` — Loom's
weakest precondition, in which every `vc`, `Triple`, `Implements` and E-edge statement of
`Verify.Basic` is stated, is `Std.WP`'s with Loom's revert predicate as exception
postcondition; both unfold to the same `match` on the model's outcome. `loom_wp_iff_stdDo` is the
same for `Std.Do`. `whileM_spec` restates Loom's `triple_whileM` as a `Std.WP` triple whose
invariant and variant are explicit arguments. All proofs: propext, Classical.choice,
Quot.sound only. So a `vcgen` proof closes the unchanged Loom goal and composes with
`triple_of_wp` / `satisfies_of_triple` as before.

## Target 2: Counter.bump's loop (`Loop.lean`, `Robust.lean`)

Statement: `Verify.CounterBump.bump_spec`, unchanged (`BumpStmt`, checked by `rfl` and by
`bump_spec : BumpStmt`).

| --- | --- | --- | --- | --- | --- | --- | --- |
| repo proof (body_step + bump_spec, Loom loop rule by hand) | annotation, by hand | 71.3 + 100.1 | 2.9 + 6.4 | 1,397 + 2,056 | 83k + 129k | ~40 | 3 std |
| vcgen + whileM_spec, grind | annotation (+ frame, pre-loop fact) | 138.8 | 46.6 | 7,249 | 898k | 4 | 3 std |

The loop is not unrolled: establishment, preservation with the decreasing variant, exit and the
fuel bound are `whileM_spec`'s VCs. Spacer's invariant does not carry the frame (slots the loop
does not write) or the pre-loop path fact `count + n < 2^256` (the Horn problem keeps it as a
guard); both are mechanical to add and were conjoined. Compared with `Verify/Infer/Reconstruct.lean`
(the same Spacer invariant checked by `omega` against hand-written Int obligations, 18 theorems,
0.45 s, not tied to the model), this proves the model's own Loom statement.

Robustness (`Robust.lean`): changing the `require` from `<=` to `<` breaks the repository's
hand proof (kept as a `fail_if_success` check) while the vcgen proof text passes unchanged
(144.6 ms).

Reading: VC generation itself is cheap and close to linear in program size (Straight: 32 to
132 ms from 16 to 128 ops); the cost and the failures are in the residual VCs (grind on nested
modular arithmetic; grind's case-split budget on 64+ guards) and in a vcgen bug on long
`if`-chains of storage reads ("unexpected let-declaration term during structural definitional
equality", Memory128/256). Shared grows about x3 to x5 per doubling in both elaboration and
kernel time: not near-linear.

## Recommendation for this layer

Adopt for the source layer behind the bridge, as an option beside `sc_vcgen`, not instead of it:
vcgen + external invariants gives 4-line loop proofs that survive source changes, with the
E-edge statements untouched. Do not switch defaults until (1) vcgen leaves the experimental flag,
(2) residual discharge is replaced by shared-fact discharge (lane G) since grind on nested
mod chains is the bottleneck, and (3) the kernel-term growth (5 to 8x on loops) is addressed by
emitting per-block lemmas (lane E). Migration path: keep `vc`/`Triple` and every E-edge statement;
add `Verify/Basic`'s bridge lemmas (as here), let a contract's `vcs` theorem pick `sd_vcgen`
or `sc_vcgen`; both produce the same statement, checked by the same axiom gate.
